# Архитектура

## Монорепозиторий

Turborepo + pnpm-воркспейсы. Все пакеты на TypeScript, Node.js 24 LTS.

```
apps/
  web     SPA: React 19, React Compiler, React Router 7, Vite, Tailwind 4, Zustand
  api     REST API: Fastify, Zod, Drizzle ORM — гости, комнаты, контакты
  core    Сигнализация и медиасервер: Fastify WebSocket + mediasoup (SFU)
packages/
  contracts          Zod-схемы и типы, общие для фронтенда и бэкенда
  db                 Схема Drizzle, миграции, подключение к PostgreSQL
  ui                 Компоненты shadcn/ui на Radix и токены темы Tailwind
  eslint-config      Общие правила ESLint (base, node, react)
  typescript-config  Общие tsconfig (base, node, react)
tests/
  e2e                Playwright: API, сигнализация, интерфейс
```

Внутренние пакеты — Just-in-Time: экспортируют исходники `.ts`. Бэкенд запускается Node.js напрямую (встроенное удаление типов), отдельной сборки нет. Фронтенд собирает Vite.

## Сервисы

```
браузер ──HTTPS──▶ Caddy (web) ──/api──▶ api  ──▶ PostgreSQL
   │                    └──/ws (WSS)──▶ core ──▶ PostgreSQL
   │                                     │
   └──SRTP/DTLS (UDP/TCP 40000+)────────▶ mediasoup workers
   └──TURN (UDP/TCP 3478, TLS 5349)─────▶ coturn ──▶ mediasoup
```

- **web** — статические файлы SPA и обратный прокси (Caddy). В разработке — Vite с прокси на `api` и `core`.
- **api** — HTTP API. Создаёт гостевые сессии, комнаты, ищет контакты. При старте применяет миграции Drizzle.
- **core** — WebSocket-сигнализация, присутствие (входящие звонки), управление комнатами в памяти и SFU mediasoup.
- **PostgreSQL** — гости, комнаты, контакты. Redis не нужен: состояние звонков живёт в памяти процесса `core`, а постоянные данные — в PostgreSQL.
- **coturn** — TURN-сервер для клиентов за строгими NAT и файрволами. Учётные данные временные (TURN REST API, общий секрет).

## Данные

| Таблица    | Поля                                                         | Назначение                                                            |
| ---------- | ------------------------------------------------------------ | --------------------------------------------------------------------- |
| `guests`   | `id`, `name`, `token_hash`, `created_at`, `last_seen_at`     | Гостевая сессия без регистрации. Токен хранится только в виде SHA-256 |
| `rooms`    | `code`, `creator_id`, `created_at`, `started_at`, `ended_at` | Комната и её жизненный цикл                                           |
| `contacts` | `owner_id`, `contact_id`, `last_call_at`                     | С кем гость уже созванивался — для поиска и приглашений               |

Комната активна, пока не завершена. Она завершается, если пустует дольше `ROOM_CLOSE_DELAY_MS` (60 секунд), или если в неё никто не вошёл за `ROOM_TTL_HOURS`.

## Звонок изнутри

1. Клиент получает статус комнаты через `GET /api/rooms/:code`.
2. Открывает WebSocket `/ws`, отправляет `hello` с токеном и `peek` — получает участников для лобби и RTP-возможности роутера.
3. После «Подключиться» отправляет `join`, создаёт send/recv-транспорты, публикует микрофон, камеру и экран, подписывается на чужие потоки.
4. Ключи сквозного шифрования участники передают друг другу через `e2eeKey` (сервер их только пересылает).
5. При обрыве WebSocket клиент переподключается и выполняет `join` с прежним `peerId`. Сервер держит участника `PEER_RECONNECT_GRACE_MS`, так что звонок не прерывается.

## Качество связи и задержка

- SFU mediasoup пересылает пакеты без перекодирования — задержка минимальна.
- Видео камеры — симулкаст VP8 в трёх слоях (180p/360p/720p, `L1T3`). Сервер подбирает слой под канал каждого получателя, клиент запрашивает нужный слой по размеру плитки.
- Аудио — Opus с DTX и FEC: устойчив к потерям в мобильных сетях.
- Клиент каждые 3 секунды оценивает RTT и потери. При плохом канале он ограничивает своё видео до 360p, показывает индикатор и предлагает режим «только звук».

## Вертикальное масштабирование

`core` запускает по одному воркеру mediasoup на ядро (`MEDIASOUP_WORKERS`, по умолчанию — число ядер). Каждый воркер слушает свой порт (`RTC_PORT + индекс`) через `WebRtcServer`, поэтому для медиа нужен лишь небольшой диапазон портов. Новые комнаты распределяются на наименее загруженный воркер. Чтобы обслуживать больше звонков, достаточно добавить ядра и увеличить число воркеров и опубликованных портов.
